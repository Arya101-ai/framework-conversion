How it works

Four steps from your suite to verified Playwright.

1Bring your suite

Keep the tests exactly as they are. Point them at the TestMu grid with a hub URL and capabilities change.

You provideExisting tests, test environment, test accounts
2Run it on TestMu

Each test becomes a session that records every browser command, its arguments and response, plus network logs, video and screenshots.

OutputA build ID with one session per test
3The TestMu MCP writes Playwright

An AI agent reads each session's command log, rebuilds steps, locators, data and assertions, and merges data-driven tests.

OutputPlaywright TypeScript, page objects, JSON test data, central config
4Compare before and after

The new tests run on the same browser and OS, under the original test names, side by side with the old build.

OutputTwo TestMu builds and a before/after report
No source codeYou don't hand over source code or rewrite anything first. The run itself is the specification.

Scope

What a log can't see, and how we close it.

Simulated example
One session, as the log records it
1
Run every data set at least once

Each branch and row gets its own session, so nothing goes unrecorded.

2
Mark inferred assertions

In the code and in the report, so each one gets a human check.

3
Don't invent checks

If the original test didn't assert something, the migration doesn't add it silently.

4
Your test owners review

Page objects and data files get reviewed before sign-off. Source code helps here, but isn't required.

Say: a log only records what happened in the browser on that run. Not visible: branches that didn't run, checks outside the browser (database, API, file), comparisons done in code, and hooks that don't touch the browser. Source: "Scope" section of the pilot one-pager.
